# Cleaning Optimization Model — Documentation

## What it does

The cleaning optimizer replaces a fixed cleaning calendar with a **daily priority list** driven by actual room usage data. Instead of cleaning every room on the same days regardless of whether anyone used them, it answers a specific question every evening:

> *Given how rooms were used today, which ones need cleaning tonight — and which can be safely skipped until tomorrow?*

This is fundamentally different from the SLA violation models. The SLA models predict whether a work order will miss its deadline. This model tells cleaning staff **where to spend their time** based on occupancy sensor data from Lentokentänkatu 11.

---

## Why this exists

SP (cleaning services) generates 60% of all work orders with a 68% SLA violation rate. A prediction model was attempted but scored AUC 0.496 — worse than a coin flip. The reason: SLA compliance for cleaning depends on *operational capacity* (how many staff are on shift, how many rooms need cleaning that day), not on the features available in the work order data.

The right question was not *"will this cleaning order miss SLA?"* but *"which rooms actually need cleaning today?"*

---

## Data source

**Silver Parquet:** `luotea-pipeline/data/silver/fact_utilization/fact_utilization.parquet`

Generated by the data pipeline from IoT occupancy sensors. One row per room per working day.

| Column | Description |
|---|---|
| `asset_name` | Room name (Coffee lounge, Varpu, K14, …) |
| `utilization_date` | Working day (weekends and public holidays excluded) |
| `utilization_pct` | Percentage of the day the room was occupied (0–100) |
| `site_id` | Always `site_valmet_l11` for this dataset |

**Coverage:** 38 rooms, January 2024 – May 2026 (628 working days per room).

## How the model works

The model has two components that run in sequence.

### Component 1 — Room clustering (run once, saved to disk)

Rooms are grouped into three usage tiers by training a K-Means clustering model on 2.5 years of historical data. Each room is described by four statistics computed across its full history:

| Statistic | What it measures |
|---|---|
| Mean utilization | How busy is this room on average? |
| Standard deviation | Is usage predictable or erratic? |
| Zero-day fraction | How often is it completely empty? |
| High-day fraction | How often does it exceed 60% usage? |

K-Means groups rooms with similar profiles. The three clusters are then labeled automatically based on mean utilization:

| Tier | Rooms | Avg utilization | Implication |
|---|---|---|---|
| **HEAVY** | Coffee lounge, Varpu, K11, K12, K14, K5, Naava, Mustikka, Norppa, Siili, Jäkälä | 45% | Accumulate dirt quickly — need frequent cleaning |
| **MEDIUM** | Ahma, Hilla, Hirvi, Joutsen, K1–K10 (most), Kaarna, Karhu, Kelo, Letto, Neva, Puolukka, Sammal, Susi, Tyrni | 32% | Moderate use — 2–3× per week |
| **LIGHT** | 2.krs Neukkari, K16, K7, Räme | 10% | Rarely used — weekly cleaning is enough |

The cluster model is saved to `models/cleaning_clusters.pkl` and only needs to be retrained when new rooms are added or the usage patterns shift significantly (quarterly is sufficient).

### Component 2 — Daily urgency score

Every evening, each room receives an urgency score (0–100) combining three signals:

```
score = 0.50 × today_utilization
      + 0.30 × rolling_3_day_average
      + 20   × min(accumulation_days / 5, 1)
```

| Signal | Weight | Why |
|---|---|---|
| **Today's utilization** | 50% | Primary signal — direct evidence of use that day |
| **Rolling 3-day average** | 30% | Captures accumulated dirt from recent days, not just today |
| **Accumulation days** (capped at 5) | 20% | Counts consecutive working days the room was used without a rest day — a room used every day for a week needs cleaning even if today was light |

**Recommendation thresholds:**

| Score | Label | Action |
|---|---|---|
| ≥ 65 | 🔴 CLEAN | Include in tonight's cleaning run — high priority |
| 35–65 | 🟡 MONITOR | Clean if capacity allows; check tomorrow if skipped |
| < 35 | 🟢 SKIP | No cleaning needed — safely skip to save resources |

## Output — the priority list

Running the model produces a ranked table sorted from highest to lowest urgency:

```
  Cleaning priority list — 2026-05-27  (Lentokentänkatu 11)

  Room                 Tier     Today    3d avg   Accum   Score   Action
  ──────────────────── ──────── ──────── ──────── ─────── ─────── ──────────
  Coffee lounge        heavy     23.1%    63.9%     8d      50.7   🟡 MONITOR
  K11                  heavy     16.7%    46.8%     7d      42.4   🟡 MONITOR
  K14                  heavy      7.7%    39.6%     7d      35.7   🟡 MONITOR
  ...
  2.krs Neukkari       light      0.0%     0.0%     0d       0.0   🟢 SKIP
```

Each row shows:
- **Today** — how much the room was used that day
- **3d avg** — average over the last 3 working days
- **Accum** — how many consecutive days it's been in use
- **Score** — the computed urgency score
- **Action** — the cleaning recommendation

The summary at the bottom reports total rooms per category and the estimated cleaning effort saved.

## How to use it operationally

### Daily routine (cleaning supervisor)

1. **Each evening, run the optimizer:**
   ```bash
   cd luotea-ml
   python3.11 scripts/cleaning_optimizer.py
   ```

2. **Read the priority list top to bottom.** All 🔴 CLEAN rooms must be done tonight. Work through 🟡 MONITOR rooms based on available staff — prioritise rooms with higher scores. Stop when staff capacity is reached.

3. **Skip all 🟢 SKIP rooms.** The data says they do not need cleaning today.

### Scoring a specific past date (for review or audit)
```bash
python3.11 scripts/cleaning_optimizer.py --date 2026-05-12
```
Use this to review what the recommendation would have been on any day in the dataset. Useful for comparing against what was actually cleaned.

### Retraining the clusters (quarterly or when rooms change)
```bash
python3.11 scripts/cleaning_optimizer.py --train
```
Reads the latest Silver utilization data, recomputes room profiles, and saves an updated `models/cleaning_clusters.pkl`. Run this if new rooms are added or usage patterns have visibly shifted over several months.

---

## How to keep the data up to date

The optimizer reads from the Silver Parquet file, which must be refreshed from the IoT pipeline before scoring. If the building's occupancy sensors push data daily, run:

```bash
cd luotea-pipeline
python3.11 -m pipeline transform --layer silver --domain iot --date $(date +%Y-%m-%d)

cd ../luotea-ml
python3.11 scripts/cleaning_optimizer.py
```

These two commands together form the complete nightly workflow.

## Example: comparing a heavy day vs a light day

**Monday 2026-05-12** (hypothetical busy day after a weekend)
- Many rooms would have 0 accumulation_days (reset over the weekend)
- Today's utilization would be high for HEAVY rooms
- Expected result: 10–15 CLEAN rooms, fewer SKIPs

**Tuesday 2026-05-27** (actual light day — 6.8% average utilization)
- All rooms have 7–8 accumulation_days (no weekend reset in the data window)
- Today's utilization was very low
- Result: 0 CLEAN, 14 MONITOR, **24 SKIP (63%)**

This variability is the point. A fixed calendar would send cleaners to all 38 rooms on both days. The optimizer sends them to the rooms that actually need attention.

## Integration with the visualization

The `score_for_date()` function in `cleaning_optimizer.py` is designed for reuse:

```python
from cleaning_optimizer import load_utilization, load_or_train_clusters, score_for_date
import pandas as pd

df = load_utilization()
clusters = load_or_train_clusters(df)
scored, date = score_for_date(df, pd.Timestamp("today"), clusters)

# scored is a DataFrame with columns:
# room, usage_tier, today_pct, rolling_3d_mean, accumulation_days,
# urgency_score, recommendation
```

The visualization can use this to render:
- A **colour-coded room map** of Lentokentänkatu 11 (red / yellow / green per room)
- A **historical heatmap** of urgency scores by room and week
- A **tier breakdown** showing which rooms belong to which cluster

## Model limitations

| Limitation | Detail |
|---|---|
| Only Lentokentänkatu 11 | Sensor data is only available for this site — Venttiilitehdas has no IoT data |
| No staffing data | The model does not know how many cleaners are on shift — it recommends priorities, not assignments |
| No cleaning history | There is no record of when rooms were actually cleaned, so the model cannot verify whether skipping was correct |
| Accumulation resets on weekends | The rolling window uses working days only — a weekend counts as a reset even if staff did not clean |

The most impactful future improvement would be feeding actual cleaning timestamps back into the model: *"room was cleaned on Tuesday"* → reset the accumulation counter rather than relying on the weekend proxy.
